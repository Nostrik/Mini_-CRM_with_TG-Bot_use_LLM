# Мини-CRM для заявок агентства

Telegram-бот принимает заявки от клиентов, сам вытаскивает из переписки имя, контакт и суть задачи, расставляет теги, а менеджеры работают с лидами в веб-интерфейсе (Streamlit).

- **Бот** общается с клиентом, при необходимости уточняет недостающее и сохраняет заявку.
- **CRM** показывает лидов, фильтрует по тегам, источнику, статусу, ищет, позволяет добавлять и править лидов вручную.
- **LLM** (через OpenRouter) используется только для разбора сообщений. Реплики бота написаны заранее, поэтому поведение предсказуемо и не ломается при сбоях модели.

## Схема работы

```
                    ┌────────────────────────── bot.py (aiogram, long polling) ──────────────────────────┐
 Клиент в Telegram  │  сообщение ─► extract_lead() ─► не хватает полей? ─ да ─► вопрос клиенту            │
 ─────────────────► │                  │   ▲                    │ нет                                      │
                    │                  ▼   │                    ▼                                          │
                    │        regex (контакты) + быстрые      db.create_lead() ─► «Заявка №N принята»     │
                    │        ответы + LLM (OpenRouter)                                                   │
                    └──────────────────────────────────────────┬─────────────────────────────────────────┘
                                                               ▼
                                                  SQLite (crm.db): leads, tags, lead_tags, users
                                                               ▲
                    ┌──────────────────────── app.py (Streamlit) ───────────────────────────────────────┐
 Менеджер/админ     │  вход ─► таблица лидов, фильтры, карточка лида, ручное добавление, теги,           │
 ─────────────────► │          пользователи (для админа)                                                 │
                    └────────────────────────────────────────────────────────────────────────────────────┘
```

Бот и CRM это два отдельных процесса. Они общаются только через файл БД (SQLite в режиме WAL, поэтому параллельные чтение и запись безопасны).

## Быстрый старт

Требуется Python 3.12–3.14 и [Poetry](https://python-poetry.org/).

```powershell
poetry install --no-root
```

1. Создайте бота у [@BotFather](https://t.me/BotFather) и получите токен.
2. Получите ключ на [openrouter.ai](https://openrouter.ai) (раздел Keys).
3. Создайте файл `.env` в корне проекта (см. [переменные окружения](#переменные-окружения)):

```
TELEGRAM_BOT_TOKEN=токен_от_BotFather
OPENROUTER_API_KEY=sk-or-v1-...
ADMIN_API_KEY=длинная_случайная_строка
```

Сгенерировать `ADMIN_API_KEY`:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

4. Запустите два процесса (в двух терминалах):

```powershell
poetry run python bot.py
poetry run streamlit run app.py
```

5. Откройте http://localhost:8501, перейдите на вкладку **«Регистрация администратора»**, введите `ADMIN_API_KEY`, имя и пароль. Дальше сотрудников создаёт администратор внутри CRM.
6. Напишите вашему боту в Telegram и убедитесь, что лид появился в CRM.

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | да | Токен бота от @BotFather |
| `OPENROUTER_API_KEY` | да | Ключ OpenRouter |
| `ADMIN_API_KEY` | да, для первой регистрации | Секретный ключ, по которому регистрируется администратор. Без него регистрация отключена |
| `OPENROUTER_MODEL` | нет | Основная модель. По умолчанию `openrouter/free` (случайная бесплатная модель) |
| `OPENROUTER_FALLBACK_MODELS` | нет | До двух запасных моделей через запятую |
| `ADMIN_CHAT_ID` | нет | Ваш chat_id в Telegram: туда бот пришлёт «запущен» и «остановлен» (узнать: команда `/id` у бота) |
| `DB_PATH` | нет | Путь к файлу SQLite, по умолчанию `crm.db`. На хостинге укажите путь на постоянном томе |
| `APP_TZ` | нет | Часовой пояс для отображения времени, по умолчанию `Europe/Moscow` (на Windows нужен пакет `tzdata`) |
| `LOG_DIR` | нет | Каталог файлов логов, по умолчанию `logs` (в Docker: `/data/logs` на томе) |
| `LOG_MAX_MB` | нет | Максимальный размер одного файла лога в МБ, по умолчанию 5 |
| `LOG_BACKUP_COUNT` | нет | Сколько старых файлов лога хранить, по умолчанию 5 |
| `LOG_TO_FILE` | нет | `0` отключает запись в файл (останется только консоль) |

Пример для стабильной работы: `OPENROUTER_MODEL=poolside/laguna-s-2.1:free`, `OPENROUTER_FALLBACK_MODELS=nvidia/nemotron-3-super-120b-a12b:free`. Список бесплатных моделей меняется, актуальные можно посмотреть командой `poetry run python list_free_models.py`.

## Функционал

### Telegram-бот (`bot.py`)

- **Сбор заявки в диалоге.** Бот собирает имя, контакт и запрос. Клиент может написать всё одним сообщением, тогда бот ничего не переспрашивает. Если чего-то не хватает, бот задаёт вопрос по недостающему полю.
- **Заявка не теряется.** Если клиент трижды не ответил на один вопрос, заявка сохраняется как есть (при отсутствии контакта подставляется Telegram-username клиента). Полный текст переписки всегда сохраняется в `raw_text`.
- **Устойчивость к сбоям модели.** Если LLM недоступна, бот работает на regex и ключевых словах и не зацикливается на вопросе.
- **Команды:** `/start` (начать заново), `/cancel` (отменить заявку), `/help`, `/status` или `/ping` (бот онлайн, аптайм, число диалогов в работе), `/id` (показать chat_id). Меню команд выставляется автоматически.
- **Уведомления администратору** о запуске и остановке бота (если задан `ADMIN_CHAT_ID`).
- **Прочее:** индикатор «печатает…», нетекстовые сообщения (фото, голосовые) получают вежливый ответ, входящий текст ограничен 2000 символами, сообщения одного чата обрабатываются по очереди.

### Извлечение данных (`extract.py`)

Три слоя:

1. **Regex** надёжно находит контакты: телефон (РФ и международные, нормализуются к `+7XXXXXXXXXX`), email, `@username`, ссылки `t.me/...`.
2. **Быстрые ответы без LLM.** LLM нужна для первого «длинного» сообщения. Короткие ответы на прямые вопросы бота разбираются кодом:
   - на вопрос об имени ответ из 1–3 слов («Ирина», «меня зовут Олег») считается именем;
   - на вопрос о задаче берётся текст как есть, теги определяются по ключевым словам (если ничего не подошло, ставится тег «другое»);
   - на вопрос о контакте понимается «tg: ник»;
   - приветствие без содержания не отправляется в модель.
3. **LLM** (строгий JSON по схеме) достаёт имя, суть запроса и теги из фиксированного списка.

Защита от ошибок модели:
- теги принимаются только из списка (`сайт`, `дизайн`, `брендинг`, `smm`, `таргет`, `seo`, `контекстная реклама`, `видео`, `чат-бот`, `консультация`, `другое`);
- контакт от модели принимается, только если он реально присутствует в тексте (защита от выдуманных номеров);
- заглушки вроде `null`, «не указано» превращаются в пустое значение;
- текст клиента передаётся в промпт как данные, а не как инструкция (базовая защита от prompt injection);
- список недостающих полей считает код, а не модель.

### Клиент OpenRouter (`openrouter_api.py`)

- Асинхронный клиент на `httpx` с методами `chat()` (обычный запрос) и `chat_json()` (ответ строго по pydantic-схеме).
- Если модель не поддерживает `json_schema`, `chat_json()` автоматически повторяет запрос, положив схему в промпт, и достаёт JSON даже из обёртки ```` ```json ````.
- Повторные попытки при 429 и 5xx с нарастающей паузой, 4xx не повторяются.
- Запасные модели (`OPENROUTER_FALLBACK_MODELS`): OpenRouter переключается на них при недоступности основной.
- Логирование времени ответа, модели и расхода токенов без записи ключей и пользовательских текстов на уровне INFO.

### CRM (`app.py`, Streamlit)

- **Вкладка «Лиды».** Таблица (ID, дата, имя, контакт, запрос, теги, источник, статус) с выбором строки. Сверху метрики: всего, новых, из бота, вручную, без тегов. Выгрузка в CSV (открывается в Excel).
- **Карточка лида** (по клику на строку): правка имени, контакта, запроса, статуса и тегов, ссылка на Telegram клиента, исходное сообщение, удаление с подтверждением.
- **Фильтры в сайдбаре:** поиск (по имени, контакту, запросу и тексту переписки без учёта регистра, в том числе для кириллицы), тег (со счётчиками и пунктом «Без тега»), источник, статус.
- **Вкладка «Добавить лида»:** ручное заведение лида с тегами. Теги можно выбрать из списка или вписать новые.
- **Вкладка «Теги»:** таблица и диаграмма: сколько лидов у каждого тега.
- **Статусы:** новый, в работе, закрыт, отказ.
- **Источники:** Telegram-бот, вручную (и зарезервировано значение «Telegram-аккаунт» под подключение личного аккаунта).

### Пользователи и доступ (`auth.py`)

- **Регистрация администратора только по секретному ключу** `ADMIN_API_KEY`. Открытой саморегистрации нет. Остальных пользователей создаёт администратор внутри CRM (вкладка «Пользователи»): имя, временный пароль, роль.
- **Роли:** администратор и менеджер. Администратор видит вкладку «Пользователи»: добавить пользователя, отключить или включить, сменить роль, удалить, сбросить пароль.
- Пароли хранятся только в виде хеша `scrypt` (стандартная библиотека). Минимум 8 символов.
- Блокировка на 5 минут после 5 неверных паролей подряд. Неверные ключи администратора тоже ограничены (5 попыток за 5 минут).
- Сообщение об ошибке входа одинаково для несуществующего пользователя и неверного пароля.
- Защита от потери доступа: нельзя удалить, отключить или понизить последнего активного администратора, нельзя менять собственную роль и отключать самого себя.
- Каждое действие сверяется с БД: отключённого пользователя выкидывает сразу.
- Любой пользователь может сменить свой пароль в сайдбаре.

### Хранилище (`db.py`)

SQLite в режиме WAL (бот и CRM работают с одним файлом параллельно), внешние ключи включены, ограничения `CHECK` на источник и статус. Теги нормализуются (нижний регистр, без лишних пробелов), поэтому «Сайт» и «сайт » это один тег. Поиск и фильтры работают в Python-функции `list_leads`, запись лида вместе с тегами атомарна.

### Логирование (`logger.py`)

Цветной вывод в консоль и файлы логов с **ротацией по размеру**: файл до 5 МБ, хранится 5 старых, поэтому диск не заполняется (лимиты настраиваются, см. переменные `LOG_*`). У каждого процесса свой файл (`bot.log`, `crm.log` или `app.log`). Уровень задаётся константой `LOG_LEVEL` (по умолчанию INFO). В логи INFO и выше не попадают тексты клиентов и ключи.

### Подбор модели (`list_free_models.py`)

Вспомогательный скрипт: запрашивает публичный каталог OpenRouter и показывает бесплатные модели со строгим JSON, отсеивая классификаторы, «думающие» модели и модели для картинок. В конце печатает готовые строки для `.env`.

```powershell
poetry run python list_free_models.py --max-size 40
```

## Модель данных

| Таблица | Поля |
|---|---|
| `leads` | `id`, `name`, `contact`, `request`, `source` (`bot` / `manual` / `tg_account`), `status` (`new` / `in_progress` / `done` / `rejected`), `raw_text`, `telegram_id`, `telegram_username`, `created_at`, `updated_at` |
| `tags` | `id`, `name` (уникальное, нормализованное) |
| `lead_tags` | `lead_id`, `tag_id` (составной ключ, каскадное удаление) |
| `users` | `id`, `username`, `password_hash`, `role` (`admin` / `manager`), `is_active`, `failed_attempts`, `locked_until`, `created_at`, `last_login_at` |

Время хранится в UTC, в интерфейсе показывается в часовом поясе `APP_TZ`.

## Тесты

Тесты написаны на `pytest`, сеть и ключи не нужны: HTTP-транспорт подменяется на `httpx.MockTransport`, LLM на заглушку, БД это временный файл.

```powershell
poetry add --group dev pytest pytest-asyncio
poetry run pytest -v
```

Покрыто: клиент OpenRouter (ретраи, запасные модели, разбор JSON, откат без `json_schema`), извлечение полей (regex, быстрые ответы, защита от выдуманных контактов, слот-филлинг, сбои LLM), БД (создание, теги, фильтры, поиск, изменение, удаление, атомарность, async-обёртки).

## Развёртывание

Бот и Streamlit общаются через файл SQLite, поэтому **на хостинге их нужно запускать в одном контейнере (сервисе) с общим постоянным томом** и `DB_PATH`, указывающим на этот том. На платформах, где у каждого сервиса свой диск (например, Railway или Render), два раздельных сервиса общий файл видеть не будут. Альтернатива: перенос на Postgres (Neon, Supabase).

В проекте для этого есть:

- `start.py`: запускает бота и Streamlit одной командой и останавливает оба, если упал любой из них (платформа перезапустит контейнер);
- `Dockerfile` и `.dockerignore`: образ с обоими процессами, база лежит в `/data`;
- `docker-compose.yml`: запуск одной командой, постоянный том с базой, автоперезапуск, healthcheck; опциональный HTTPS через Caddy (`Caddyfile`);
- `DEPLOY.md`: пошаговая инструкция для VPS и платформ с поддержкой Docker, резервные копии, разбор типичных проблем.

```bash
docker compose up -d --build
```

Запускать нужно ровно один экземпляр сервиса. На хостинге все переменные из таблицы выше задаются в настройках сервиса, файл `.env` в образ не попадает.

## Безопасность и персональные данные

- В CRM лежат контакты и тексты обращений клиентов, то есть персональные данные. Доступ только по логину и паролю, пароли хешируются.
- Файлы `.env`, `crm.db` и `logs/` должны быть в `.gitignore`.
- Ключи API и пароли не пишутся в логи, тексты клиентов попадают только в DEBUG и в обрезанном виде.
- `ADMIN_API_KEY` знает только владелец системы: по нему можно создать администратора. Храните его только в переменных окружения.
- При использовании бесплатных моделей OpenRouter тексты сообщений уходят стороннему провайдеру модели. Для реальных клиентов выбирайте модели и провайдеров с подходящими условиями обработки данных.

## Ограничения и план развития

Не реализовано в текущей версии:

- **Подключение обычного Telegram-аккаунта** (входящие сообщения аккаунта как лиды): в схеме уже есть источник `tg_account`, подход описан в отчёте.
- Дубликаты лидов (один и тот же клиент пишет повторно), назначение ответственного менеджера, история изменений.
- Постоянные сессии в браузере (после перезагрузки страницы нужно войти заново), восстановление пароля по почте.
- Состояние диалога бота хранится в памяти и теряется при перезапуске.

Идеи: уведомление менеджеру в Telegram о новой заявке, канбан-доска по статусам, кнопка «Поделиться контактом» в боте, распознавание голосовых, перенос на Postgres, CI с запуском тестов.
